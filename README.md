# Kufar Sniper 4.0.1

Рабочая версия для одного Telegram-чата. Цель этого обновления — сохранять данные и повторять незавершённую работу. Точность цены сделки пока не измерена: текущий алгоритм оценивает цены объявлений.

## Что запускать

Использовать **весь проект версии `v4.0.1`**, запускать через `runner.py`. Одного файла `sniper.py` теперь недостаточно. Потолок фонового сбора по умолчанию — **5500 BYN**, бюджет уведомлений по умолчанию — прежние 120–750 BYN. Сохранённые пользовательские настройки имеют приоритет.

Текущий этап — несколько недель накопления данных и контроля качества; возвращение к перепродаже отложено. Локальные проверки и миграция копии настоящей БД из `debon25/snipser` пройдены. Сама рабочая смена, Telegram, загрузка в Release и сервер пока не переключались. Никакая подписка не куплена, бот в Telegram не запускался. Подробности — в `docs/PRODUCTION_MIGRATION.md`.

## Локальная проверка

В этой рабочей копии уже создана `.venv` с установленными зависимостями. Команды PowerShell из папки проекта:

```powershell
.\.venv\Scripts\python -X utf8 -m unittest discover -s tests -v
.\.venv\Scripts\python -m pip check
```

Для новой рабочей копии окружение создаётся заново:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
```

Проверки используют временные базы и имитацию отказов внешних сервисов. Это не проверка боевой БД.

## Подключение существующей БД

Сначала остановить прежний бот. Получить его БД и настройки либо подтверждённый снимок. Для действовавшего проекта **не использовать `--initialize`**: отсутствие файла считается потерей состояния, запуск останавливается.

Для Linux выбранные рабочие пути: `/var/lib/kufar-sniper/sniper.db` и `/var/lib/kufar-sniper/settings.json`. Код и отдельные окружения версий — в `/opt/kufar-sniper/releases/`, активная версия — ссылка `/opt/kufar-sniper/current`.

Первый запуск `runner.py` на существующей БД делает проверенный снимок до миграции. Снимок старой схемы получает имя `pre-v40-...zip` и не удаляется автоматической ротацией. Миграция добавляет таблицы и поля, сохраняет историю цен и прежние эвристические значения отдельно. Активные неуведомлённые лоты из старой ML-таблицы возвращаются в обработку.

## Восстановление

Проверка и распаковка в **новую** папку, без вмешательства в работающую БД:

```text
python state_store.py restore-local --archive backups/SNAPSHOT.zip --db recovery/sniper.db --settings recovery/settings.json
python state_store.py check --db recovery/sniper.db
```

При восстановлении проверяются SHA256, перечень файлов, SQLite `integrity_check`, число строк всех таблиц и JSON настроек. Для замены рабочей БД остановить службу и таймеры; только затем использовать `--overwrite`. Прежняя исправная БД сохраняется снимком; повреждённая сохраняется отдельным файлом `unverified-before-restore-*.db`.

Блокировка запрещает восстановление поверх БД, которой пользуется `runner.py`. Маркер `*.restore-in-progress` после аварии запрещает запуск с возможной смесью БД и настроек. В этом случае восстанавливается выбранный снимок в новый каталог, проверяется, затем производится переключение; маркер не следует просто удалять для продолжения работы.

Снимок возвращает состояние **на момент снимка**. Сообщения, отправленные после него, могут повториться при откате БД. Для отката кода внутри v4 обычно сохраняется текущая БД.

## Постоянный запуск

Основной подготовленный вариант — Ubuntu/Debian VPS, `systemd`, один процесс, постоянный диск. Файлы находятся в `deploy/`:

- `prepare-release.sh v4.0.1` готовит отдельный каталог версии, окружение, зависимости и запускает тесты. Бота не запускает.
- `activate-release.sh /opt/kufar-sniper/releases/ИМЯ_ВЕРСИИ` проверяет наличие БД, останавливает предыдущую службу, делает снимок, переключает код и запускает службы.
- `kufar-sniper.service` перезапускает завершившийся процесс через 30 секунд и контролирует зависание через watchdog.
- Почасовой таймер создаёт проверенные снимки. Ротация хранит 24 последних снимка и по одному за последние 14 представленных дней; вручную названные и `pre-v40`-снимки сохраняются.
- Проверка состояния каждые 5 минут обнаруживает давность ленты, зависание, очередь отправки и недостаток диска. Ошибки видны в журнале `systemd`; внешние аварийные оповещения пока не подключены.
- Отдельный **не включённый автоматически** таймер `kufar-sniper-offsite` публикует ежедневный снимок в выбранный GitHub Release. Для него нужны `gh`, репозиторий `db-state` и отдельный файл `/etc/kufar-sniper-backup.env` с токеном.

Секреты службы — `/etc/kufar-sniper.env`, права 600. Пример `.env.example` не загружается Python автоматически: окружение передаёт `systemd`. После доступа к серверу настройку и проверку выполняет помощник; эти файлы — подготовка, а не требование самостоятельно писать Python.

После активации проверить журнал, свежесть ленты, доставку в разрешённый чат, остановку/перезапуск, почасовой снимок и восстановление **скачанной внешней копии** в отдельную папку. Затем провести 24-часовую проверку стабильности.

## Обновление и откат

Подготовить новый тег в отдельном каталоге через `prepare-release.sh`, выполнить тесты, затем активировать каталог. Старый код сохраняется, ссылка `previous` указывает на предыдущую версию. Для отката между совместимыми версиями v4 повторно активировать прежний каталог, сохранив текущую БД.

Откат до `baseline-3.9` требует отдельной копии БД **до миграции**, остановки бота и осознанного восстановления старой пары «код + БД». Возврат одного `sniper.py` вернёт исправленные ошибки. Не заменять текущую БД старой ради обычного отката кода.

## GitHub Actions как временный вариант

Workflow по умолчанию выключен условием `SNIPER_ACTIONS_ENABLED`. Не запускать его одновременно с VPS: локальная блокировка не защищает от второй машины.

Для Actions нужны `TG_TOKEN`, `TG_CHAT_ID`, при необходимости `PROXY_URL`; `DB_REPO` указывает на репозиторий состояния; по умолчанию это текущий репозиторий. Для отдельного репозитория `DB_REPO_TOKEN` даёт доступ к нему. Публичный `debon25/snipser` поддерживается без обязательного создания ещё одного репозитория. Файлы Release доступны читателям выбранного репозитория; приватное хранение можно настроить отдельно. Сначала должен существовать релиз `db-state` с проверяемой БД. Автоматического создания пустой БД или возврата к старому Actions Cache нет.

Снимок публикуется под уникальным именем, скачивается обратно и проверяется; затем публикуется отдельный маркер готовности. Старые файлы не заменяются. Смена создаёт `sniper-run-ID.start.json`; только успешное сохранение создаёт `.done.json`. Незаконченная смена блокирует восстановление старой версии для следующего запуска.

Если сохранение упало: получить `sniper-recovery-*` из workflow, проверить БД/снимок, опубликовать восстановленную новую версию, затем закрыть **именно незавершённый** run через `state_store.py finish-run --run-id ID --archive SNAPSHOT.zip`. Нельзя просто удалить `.start.json`, принять старую БД за актуальную или запускать пустую. В публичном репозитории кода аварийный artifact создаётся только для публичного источника БД; данные отдельного приватного хранилища туда не публикуются.

Цепочка включается отдельно переменной `SNIPER_CHAIN_ENABLED=true`. Следующая смена допускается после ошибки бота, если состояние успешно сохранено. Ошибка восстановления/сохранения останавливает цепочку; это защита данных. Дополнительный cron каждые 6 часов даёт попытку возобновления после исправления, но не гарантирует непрерывность.

У Release есть лимит 1000 файлов. Когда файлов уже больше 950, новая смена блокируется; старые версии нужно архивировать отдельно и провести проверку восстановления перед очисткой. Автоматического удаления внешних снимков нет.
