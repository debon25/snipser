# Проверка шести проблем

Основание — переданные файлы и воспроизводимые проверки. Копия настоящей БД из релиза db-state получена и проверена; рабочий запуск не изменялся.

## Проверка 1. Сохранение и восстановление БД

В исходном YAML использован `gh release upload --clobber`; отсутствующий файл/релиз считается первым запуском. Исправлено: уникальные архивы, SHA256, проверка SQLite, обратное скачивание, отдельный маркер готовности. Потеря БД останавливает запуск. Старый `sniper.db` читается для однократной миграции.

## Проверка 2. Повтор обработки и уведомлений

Сохранение предшествовало оценке, а неизменившаяся цена приводила к пропуску. Исправлено: постоянные `feed_inbox` и `notification_outbox`, повтор с задержкой, восстановление незавершённой отправки. Старые активные неуведомлённые записи из ML-таблицы возвращаются в очередь.

## Проверка 3. Исчезновение и предполагаемая продажа

HTTP 404/410 и неактивный статус преобразовывались в `sold`/`sold_fast`, цена умножалась на 0.75–0.95. Исправлено: состояние `unavailable`, отдельные времена наблюдения активности и обнаружения недоступности. Продажа, срок и цена сделки не выводятся из исчезновения. Старые статусы и оценки сохранены в `legacy_*`.

## Проверка 4. Возраст активных объявлений

Медиана возраста активной выборки была подписана «ликвидность». Подпись исправлена; она не обозначает срок продажи. Калибровка цены по предполагаемым продажам отключена.

## Проверка 5. Пагинация и пропуски

Основная лента читала только 50 записей. Теперь читаются до 4 страниц за цикл, включая свежую первую страницу и сохранённое продолжение. Страница записывается вместе с курсором. Дубли объединяются по ID; незавершённая обработка сохраняется независимо от выдачи. Границы покрытия перечислены ниже.

## Проверка 6. Цепочка смен

Dispatch зависел от успешного бота, резервный cron был раз в 12 часов. Теперь следующая смена допускается после ошибки бота при проверенном сохранении; есть повтор dispatch и cron каждые 6 часов. Ошибка состояния останавливает цепочку, чтобы не продолжить со старой БД. Для постоянной работы подготовлен `systemd`.

## Доставка и дубли

Ключ уведомления — ID объявления и цена в копейках. Подтверждённая отправка той же цены не повторяется при обычном обходе, повторной оценке или перезапуске с той же БД. Новая подходящая цена может создать новое уведомление.

Устаревшая неотправленная цена отменяется при новой цене. Перед отправкой проверяются доступность и текущая цена карточки. Смена настроек отменяет старые неотправленные карточки и возвращает исходные объявления на оценку. При HTTP 429 сохраняется указанная Telegram задержка. Неудача с фотографией не запускает немедленно второе сообщение при неопределённом сетевом результате.

Гарантия — **повтор до подтверждения результата**, а не строго одна доставка при любых сбоях. Если Telegram принял сообщение, а ответ потерялся либо процесс завершился до записи подтверждения в SQLite, повтор может дать дубль. У Bot API `sendMessage` нет параметра идемпотентности для клиента; успешный ответ возвращает объект Message. [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

Восстановление старого снимка тоже возвращает старую историю отправок. Поэтому после неподтверждённого сохранения смена не продолжается молча с предыдущей БД.

## Сохранность данных

Снимок создаётся через SQLite backup, а не простым копированием работающего файла. Проверяются сама БД и настройки. При сохранении смены сравниваются исходные ID лотов и записей, а история цен, наблюдений и версий проверяется на сохранность прежних строк. Одного размера файла или суммарного числа строк недостаточно.

В `ad_revisions` сохраняются изменившиеся ответы ленты и карточек; одинаковые ответы повторно не записываются. Источник восстановленных старых записей помечен `legacy_reconstructed`. История, которую прежний код вообще не записал, не может быть восстановлена из одних исходников.

Старые «проданные» записи не получают выдуманного точного времени последней активности: известно лишь то, что оставил прежний код. Для новых наблюдений `last_active_ts` и `unavailable_detected_ts` разделены. Пустой/неправильный ответ HTTP 200 считается ошибкой данных, а не доказательством исчезновения.

## Границы покрытия

Курсорный обход ограничен по нагрузке и постепенно проходит старую выдачу. Это не мгновенная загрузка всего рынка и не гарантия перехвата объявления, которое исчезло между запросами. При истёкшем курсоре обход начинается заново; при временной ошибке курсор сохраняется, запросы замедляются. Старые правки могут обнаруживаться позднее свежей ленты.

Обработка ограничена 10 объявлениями и примерно 30 секундами за пакет; уже начатый сетевой запрос завершается в пределах собственного таймаута. Это уменьшает задержку опроса свежей ленты при первоначальном накоплении. Реальную скорость, размеры очередей, лимиты Kufar и длительность полного обхода нужно измерить на длительном запуске.

Проверка исчезнувших объявлений также идёт ограниченными пачками. В большой БД обнаружение недоступности может запаздывать. Отсутствие в поисковой выдаче само по себе не считается исчезновением.

2. Успешная отправка и повтор в одном разрешённом Telegram-чате.
3. Сохранение и восстановление из настоящего `db-state`, включая отказ загрузки.
4. Работа `systemd`, перезапуск сервера, watchdog, таймеры и свободный диск.
5. Сутки работы с измерением свежести ленты и очередей. Затем независимая проверка точности цены — техническая надёжность её не доказывает.
